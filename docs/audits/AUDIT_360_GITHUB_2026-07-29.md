# 360° Audit — GitHub Integration Subsystem

**Date:** 2026-07-29
**Scope:** Focused audit of the GitHub App / git-push / GitHub-REST subsystem
(all 6 pillars applied to this slice; full-system coverage already exists in
`AUDIT_PRODUCTION_READINESS_2026-07-21.md`).
**Codebase version:** v0.6.1
**Method:** Findings are backed by file:line references verified against live
source. Two top findings (App key not vaulted; git missing from Dockerfile)
were independently re-verified before being marked High.

**Overall (this subsystem): 68/100**

**Strengths**
- ✅ `http.extraheader` + `GIT_CONFIG_*=nul` auth is correct cross-platform and uniformly applied across push/pull/rebase — the hardest bug in this subsystem, solved.
- ✅ Verify-push-landed (`ls-remote`) logic — refuses to report success for a no-op push. Genuinely robust design.
- ✅ Token redaction is complete in every log line and return path of `_git_sync`.
- ✅ Vault (AES-256-GCM, PBKDF2 600k, random salt) is sound *when a key routes through it*.
- ✅ JWT tests do real RS256 signature verification; `IdeService.resolve()` has a two-layer path-traversal guard.
- ✅ Dockerfile runs non-root; CI secrets use `${{ secrets.* }}`.

**Critical risks**
- 🚨 GitHub App **private key is never encrypted** even when the vault is enabled.
- 🚨 GitHub **PAT written plaintext to `.env`** regardless of vault.
- 🚨 `git` binary **not installed in the production Docker image** — every git tool fails there.

**Primary opportunities**
- Unify token-resolution precedence across `_git_sync` / `GitHubClient` / httpx fallbacks.
- Add real-git (local-bare-remote) integration tests for the push auth path.
- Add gitleaks + extend bandit to `kazma-skills`.

## 2. Comprehensive Findings & Fixes

### 🔒 Security & Secrets

#### 🚨 S1 — GitHub App private key not encrypted even with vault on
- **Where:** `kazma-core/kazma_core/config_store.py:62-74` (`is_sensitive_config_key`)
- **Issue:** The sensitive classifier takes the **last dotted segment** of the key (`key.rsplit(".",1)[-1]`). The App key is stored under `connectors.github.app_private_key` → last segment is `app_private_key`, which is **not** in `_SENSITIVE_LAST_SEGMENTS` (the set has `private_key`, not `app_private_key`) and doesn't end in a recognized suffix. Verified at runtime: `is_sensitive_config_key("connectors.github.app_private_key") → False`.
- **Impact:** A PEM posted to `POST /api/github/app/config` (`github.py:119-141`) lands **plaintext in `settings.db`/Postgres even when `KAZMA_VAULT_KEY` is set**. Directly contradicts the vault's promise (existing audit M5).
- **Fix:**
```python
# config_store.py — add the App-key segments to the sensitive set
_SENSITIVE_LAST_SEGMENTS = frozenset({
    ...
    "private_key",
    "app_private_key",        # ← ADD
    "app_private_key_path",   # ← ADD (path to a key is also sensitive)
    "app_id",                 # ← ADD (installation identity)
    "app_installation_id",    # ← ADD
    ...
})
```
Plus a migration that re-classifies any existing plaintext `connectors.github.app_*` rows into the vault.

#### 🚨 S2 — GitHub PAT written plaintext to `.env`
- **Where:** `kazma-gateway/kazma_gateway/routers/github.py:53-87` (`save_github_token_to_env`), called by `POST /api/github/token` (98-116).
- **Issue:** The PAT is mirrored to `<cwd>/.env` as `GITHUB_TOKEN=...` in cleartext, in addition to (vault-able) ConfigStore. The `.env` mirror is **always plaintext**.
- **Impact:** World-readable credential on disk; the vault setting gives a false sense of protection.
- **Fix:** Stop mirroring to `.env`. Persist only via `get_config_store().set("connectors.github.token", token, "connectors")` (which routes through vault classification). If `.env` is needed for subprocess `GITHUB_TOKEN`, write it to a `0600` file under `data_dir`, not the repo `.env`.

#### 🟧 S3 — `.gitignore` has no private-key patterns
- **Where:** `.gitignore`
- **Issue:** No `*.pem`, `*.key`, `id_rsa*`, `*.ppk`. Since `app_private_key_path` lets users point at a PEM on disk, a misplaced key can be committed.
- **Fix:** Add `*.pem`, `*.key`, `id_rsa*`, `*.ppk`, `private-key*` to `.gitignore`.

#### 🟡 S4 — `_app_token_cache` is an unlocked module-global (TOCTOU)
- **Where:** `kazma-core/kazma_core/git_identity.py:178`, `181-192`, `317-399`
- **Issue:** Read-mint-write sequence has no lock. A concurrent `invalidate_app_token_cache()` + `mint(force=True)` can briefly resurrect a revoked `ghs_*`, and N concurrent failing pushes trigger N redundant GitHub mints (no single-flight).
- **Impact:** Wastes GitHub API budget; tiny stale-token window. Not a correctness crash (CPython dict writes are GIL-atomic).
- **Fix:** Wrap cache access in a `threading.Lock` (sync code) with double-checked locking on mint; or make the mint async with an `asyncio.Lock`.

#### 🟢 S5 — `file_write` traversal guard weaker than `IdeService`
- **Where:** `kazma-core/kazma_core/tools/file_write.py:57-104`
- **Issue:** Uses `target.resolve().relative_to(workspace)` only. `resolve()` follows symlinks, so it can be fooled on symlinked workspaces; no string-normalization backstop like `IdeService.resolve()` (`ide/service.py:112-162`).
- **Fix:** Adopt `IdeService`'s two-layer pattern (string `..` check + `normpath` containment) in `file_write`.

### 🏗️ Architecture & Code Health

#### 🟧 A1 — Inconsistent token-resolution precedence across surfaces
- **Where:**
  - `_git_sync` (`tools.py:109-121`): **App token first**, then OAuth/PAT/env.
  - `GitHubClient.get_github_token` (`github_client.py:79-105`): **OAuth/PAT first**, App token fallback.
  - httpx fallback in `github_*` tools (`tools.py:503-505`, 546, 584, 621, 667): **only `GITHUB_TOKEN` env**.
- **Issue:** Three different orders. The git-vs-REST difference is *intentional and documented*, but the **third path is a real gap**: in a headless App-only deployment, `github_create_pr`/`merge_pr`/`create_issue`/`comment_issue`/`list_issues` silently fall back to env-only and ignore App/OAuth/PAT — they fail while `git_push` works.
- **Fix:** Route the httpx fallback through the same resolver the tools use; at minimum call `get_github_token()` instead of bare `os.getenv`.

#### 🟧 A2 — Owner/repo regex divergence
- **Where:** `_resolve_owner_repo` (`tools.py:717`) uses `[^/]+?` (allows `.`); `parse_github_slug` (`github_client.py:114`) uses `[^/\.]+?` (excludes `.`).
- **Impact:** A repo slug containing `.` (e.g. `foo.bar`) parses differently between the two paths → inconsistent owner/repo for the same workspace.
- **Fix:** Delete `_resolve_owner_repo`'s regex; reuse `parse_github_slug`.

#### 🟧 A3 — Detached-HEAD push silently does the wrong thing
- **Where:** `_git_sync` (`tools.py:134-137` resolves branch; `175-180` builds refspec)
- **Issue:** In detached HEAD, `git branch --show-current` returns `""`, so `target_branch=""`, and neither `--set-upstream` nor the refspec branch is appended → the push runs with **no refspec**, pushing nothing useful (or all matching refs per `push.default`).
- **Fix:** Detect empty `target_branch` and return an explicit error: *"Cannot push from detached HEAD — checkout a branch first."*

#### 🟢 A4 — REST fallbacks duplicate endpoint/status logic across 5 tools
- **Where:** `tools.py:506-518, 546-561, 584-599, 620-635, 666-681`
- **Issue:** Each `github_*` tool has a primary (`GitHubClient`) path and an inline httpx fallback reimplementing URLs/headers/status checks.
- **Fix:** Extract a shared `_gh_request(method, path, json)` helper used by all five tools.

### ⚡ GitHub Integration & API Efficiency

#### 🟡 G1 — No rate-limit backoff/retry
- **Where:** `GitHubClient.request` (`github_client.py:263-276`)
- **Issue:** Detection exists (`_is_rate_limited`, `_rate_limit_reset`) and errors surface `rate_limited=True`, but there is **no sleep-until-reset, no backoff, no retry**. GitHub secondary limits (403/429 without `remaining=0`) are misclassified as generic errors.
- **Fix:** On rate-limit, optionally sleep until `X-RateLimit-Reset` (bounded) and retry once; treat 429 and `retry-after` as rate-limit signals too.

#### 🟢 G2 — No webhook surface (by design, not a vuln)
- **Where:** `gateway.py:3` — "Headless architecture: NO public IP, NO HTTPS tunnels, NO webhooks."
- **Note:** There is no GitHub webhook receiver and no `X-Hub-Signature-256` verification to perform. GitHub is outbound-only. Document this explicitly so future readers don't mistake it for a missing control.

#### ✅ G3 — App-token git auth is correct (post-fix)
- `_git_sync` uses `Authorization: Basic base64("x-access-token:<ghs_>")` via `http.extraheader`, applied to every request; `credential.helper=` + `GIT_CONFIG_*=nul` prevent credential-manager interception. This is the correct cross-platform approach (the URL-token method is silently broken on Windows/schannel — documented inline at `tools.py:155-164`).

### 🧪 Testing & Reliability

#### 🚨 T1 — The push/pull auth path has ZERO real-git coverage
- **Where:** `test_github_app_integration.py` — every push/pull test `patch("subprocess.run")`.
- **Issue:** The most platform-bug-prone code (`http.extraheader`, `GIT_CONFIG_*=nul`, verify-landed) is tested only against canned `MagicMock` outputs. No test asserts the command contains `-c http.extraheader=Authorization: Basic ...`. `test_git_bot_commit.py` is the only real-git test and covers local commit identity only.
- **Impact:** A regression in the exact auth construction (the bug that cost hours this session) would not be caught.
- **Fix:** Add (a) assertions that the built command includes `http.extraheader` + `credential.helper=`; (b) one real-git integration test using a local bare remote (`git init --bare`) to exercise push/pull/verify end-to-end without GitHub.

#### 🟡 T2 — `ls-remote` verify logic tested only with canned strings
- **Where:** `test_git_push_pull_detects_false_up_to_date` (line 195) uses `mock_ls_fail` canned stdout.
- **Fix:** Covered by T1's real-git test (real `git ls-remote` output format).

#### 🟢 T3 — No tests for `git_status`, `git_checkout`, `git_merge`, `_resolve_owner_repo` regex divergence, detached-HEAD push.
- **Fix:** Add unit tests for each; the detached-HEAD case pins A3.

### 🚀 DevOps, Deployment & CI/CD

#### 🚨 D1 — `git` binary not installed in the production Docker image
- **Where:** `Dockerfile:6-10` installs only `build-essential curl libpq5`. (The demo `Dockerfile.demo:8` does install git.)
- **Impact:** Inside the prod container, `git_status`/`git_push`/`git_commit`/etc. fail with `FileNotFoundError`. The entire git tool surface is broken in the shipped image.
- **Fix:** Add `git` to the `apt-get install` list in `Dockerfile`.

#### 🟧 D2 — Bandit excludes `kazma-skills`
- **Where:** `.github/workflows/ci.yml` bandit job scans `kazma-core`, `kazma-gateway`, `kazma-ui` but **not `kazma-skills`** (where all the `subprocess.run` git calls live).
- **Fix:** Add `kazma-skills` to the bandit scan path.

#### 🟧 D3 — No secret-leak scanning (gitleaks/trivy)
- **Where:** CI has bandit (Python AST) but no commit/secret scanner.
- **Fix:** Add a gitleaks step; this would have caught the `.git/config` token leak class of issue at commit time.

#### 🟡 D4 — Dockerfile not multi-stage; ships `build-essential`
- **Where:** `Dockerfile:7` (single stage, compiler toolchain in final image).
- **Fix:** Multi-stage build; drop `build-essential` from the runtime stage.

#### 🟡 D5 — `COPY . .` can bake secrets into the image
- **Where:** `Dockerfile:13`. Relies on hygiene + `.gitignore`; no `.dockerignore` verified.
- **Fix:** Add a strict `.dockerignore` (exclude `.env`, `*.pem`, `.git/`, `kazma-data/`, `.kazma/`).

#### 🟢 D6 — CI hygiene (low)
- No `permissions:` block on `ci.yml` (defaults to write on main); `fail_ci_if_error: false` on coverage; `build-docker` skipped on PRs.
